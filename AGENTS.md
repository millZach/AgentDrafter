# AgentDrafter

AgentDrafter is an open-source CAD engine built for agents first. An agent creates, revises and checks technical drawings with no window open; a reviewer watches, accepts or undoes. It reads and writes DWG without AutoCAD, runs on Windows, Linux and macOS, and does 2D first and 3D after. The drawings it handles go to real plants, which keep them as master records.

This is a brief, not a specification. It names what is expensive to get wrong and leaves the rest to you. Where it does not reach, work out what AgentDrafter would do from `CONTEXT.md`, the ADRs and `docs/plan.md`, and say in the pull request what you worked out.

**Status: walking skeleton.** `agentdrafter build` turns a sheet description that holds lines, polylines with arc segments and widths, arcs, circles, ellipses, splines, donuts, 2D solids and hatches on layers with linetypes, each in its layer's colour, linetype and lineweight or its own, text and multiline text in TrueType and SHX text styles, inserts of blocks with attributes from a block library, and tables in table styles, into a DWG in the 2018 format, and given a drawing set's folder builds one DWG per row of its data, each a template filled in from the row; `agentdrafter schema` prints what a sheet description may hold (`schema block-library`, `template`, `set` and `rows` for the other kinds of file), `agentdrafter measure-text` measures how wide text draws, `agentdrafter render` draws a sheet to a PNG stamped with the record it came from, `agentdrafter plot` draws a sheet, a DWG or every sheet of a drawing set to a PDF at its exact sheet size, through a CTB plot style, with searchable text, stamped as the PNG is, `agentdrafter query` asks a drawing set's records for objects by ID, name, block, attribute or text, the blocks on each sheet, inserts' attributes, a distance and a sheet's extents, and `agentdrafter change` applies a change set of typed operations, adding, changing, moving and deleting objects and setting attribute values, to a drawing set's own files and builds again the DWGs of the sheets it touched, each sheet fully or not at all, with `agentdrafter operations` listing the operations with their AutoCAD aliases and schemas, `agentdrafter journal` lists the change sets and failed attempts the set's folder records, and `agentdrafter undo` undoes a change set and every later one from it, byte for byte, in a later session as in the same one, `agentdrafter accept` issues the working revision, refused while the set is inconsistent and warning of failed checks, after which its change sets cannot be undone and outputs made from it say so in their stamps, and `agentdrafter check` re-reads a drawing set's saved files and reports each check a sheet fails, the exact paper size, nothing off the sheet, no text overflowing its cell, no text on other text and no line through a text's letters, as a change set's reply does for the sheets it landed on, and `agentdrafter import-blocks` reads a DWG's or a DXF's blocks into a block library of its own, as AutoCAD's DesignCenter does, as a change set's `import_blocks` does into a set's; `agentdrafter serve` serves every command as a local HTTP API and `agentdrafter mcp` as an MCP server, both taking their commands from one registry in the core, as the command line does, and `serve` also serves the viewer, a page that draws a drawing set's sheets in the browser, from the display list `agentdrafter display-list` gives, with the drawing pipeline compiled to WebAssembly, pans and zooms them on a laptop and a phone, shows each change set as it lands, from any interface, through an event stream of the set's journal, steps back through the journal, inspects the object the reviewer picks, and undoes and accepts; so does the Python library, a binding to the core with every command as a function; one pip package per system carries the core, the command with both servers and the library, which CI builds and tests on every system and nothing publishes yet; every object carries its ID into its DWG; nothing else is built yet. `docs/plan.md` holds the agreed plan. The stack is decided: a Rust core that reads and writes DWG through acadrust, a Python binding and thin interfaces over it, and a browser viewer that draws with the same Rust code compiled to WebAssembly, with TypeScript and React around it.

## What is expensive to get wrong

- **The repository is public.** No plant's drawing, block, tag or name enters it, ever, including in tests, fixtures, screenshots, logs and notes. Tests and examples use the demo plant, which is made up. A bug found on a real drawing is reproduced on a made-up drawing before its test is committed (ADR-0008).
- **Untouched means unchanged.** When AgentDrafter revises an existing DWG, everything it did not edit comes back exactly as it was, including content it does not understand. A revision is saved in the DWG version its original arrived in (ADR-0006). A drawing the reader cannot fully decode is not revised unless the reviewer allows it for that drawing. A change that touches DWG reading or writing proves this against AutoCAD, not by eye (ADR-0004).
- **An original is never overwritten.** An existing DWG is read-only. A change is saved as a new revision beside it.
- **The engine knows drawings, not trades.** Nothing about loops, wires, terminals or any trade goes into the engine. That belongs in a generator (ADR-0002).
- **Every interface behaves the same.** The command line, the MCP server, the Python library and the HTTP API are thin layers over one core. Drawing logic in an interface is a bug (ADR-0007).
- **A sheet is never left half-edited.** Each sheet takes its part of a change set fully or not at all (ADR-0005).
- **The licence is Apache-2.0.** No code is copied from a GPL project, such as Open CAD Studio or LibreDWG. Check a dependency's licence before adding it: permissive and MPL-2.0 are fine, anything stronger needs a decision (ADR-0010).
- **acadrust is pinned.** Moving the pin means running the judge again. Fixes to acadrust go upstream, not into a private patch (ADR-0009).

## Run, test and prove

The code is one Cargo workspace. `crates/agentdrafter-core` is the core, the library that knows drawings; its entry points take and return plain data, and acadrust sits behind its one seam, `src/dwg.rs` with its submodules in `src/dwg/`. The one drawing pipeline (ADR-0011) is `src/draw/`, which turns a sheet into a display list, `src/raster.rs`, which turns that into pixels, and `src/pdf.rs`, which turns it into a PDF; none of them touches the file system, so the core builds for WebAssembly, which CI checks. `crates/agentdrafter-cli` is the `agentdrafter` command, a thin layer that prints the core's reply as JSON, with the HTTP API (`src/http.rs`) and the MCP server (`src/mcp.rs`), thin layers too; its code is a library, `src/lib.rs`, which the binary and the pip package's command both run; the HTTP API also serves the viewer's page (`src/page.rs`), which `build.rs` embeds from `viewer/dist/` when it has been built. `crates/agentdrafter-viewer` is the viewer's renderer, which draws a display list with WebGL2 in the page, compiled to WebAssembly; `viewer/` is the page, TypeScript and React built with Vite. `crates/agentdrafter-py` is the Python library's extension, a binding to the core, with the library's Python in `python/agentdrafter/`, its tests in `python/tests/` and the package in `pyproject.toml` (`docs/python.md`). Every interface takes its commands from the core's registry, `src/commands.rs`: a new command goes there, with its input's schema, and gets a command-line form in `lib.rs`, and a test fails until it has one and until `tests/calls.json` holds a call of it, which `tests/servers.rs` and the Python library's tests run through every interface. The Rust toolchain is pinned in `rust-toolchain.toml`.

- Build: `cargo build --workspace`. On forge, add `-j4` and keep `target/` inside the checkout, not under `/tmp`.
- Run: `cargo run -p agentdrafter-cli -- build examples/one-line.yaml` writes `examples/one-line.dwg` and prints one line of JSON. Add `--overwrite` to build it again. `examples/geometry.yaml` holds every kind of line and curve, `examples/hatch.yaml` holds hatches, `examples/text.yaml` every kind of text, `examples/blocks/` a block library with two sheets that insert its blocks, `examples/demo-set/` a drawing set, built with `build examples/demo-set`, and `examples/demo-plant/` the demo plant's eight loop sheets, which CI builds, plots and checks on every system and holds to the same bytes on all three; `cargo run -p agentdrafter-cli -- schema` prints the sheet description's JSON Schema, `cargo run -p agentdrafter-cli -- render examples/geometry.yaml` draws it to `examples/geometry.png` (`docs/render.md`), `cargo run -p agentdrafter-cli -- plot examples/demo-set` plots the demo set's sheets to PDF (`docs/plot.md`), and `cargo run -p agentdrafter-cli -- change <set> <change-set.json> --dry-run` shows what a change set would do to a copy of a set, without writing (`docs/change-sets.md`).
- Fonts: AutoCAD's SHX fonts are Autodesk's and never enter the repository, not even in a test. Text is measured with the fonts in the folders `AGENTDRAFTER_FONTS` lists (or `--fonts`), such as AutoCAD's `Fonts` folder on a machine that has AutoCAD; anywhere else a look-alike is used and the reply says so. Tests write their own made-up fonts.
- Plot styles: AutoCAD's CTB files are Autodesk's too and never enter the repository, not even in a test. A plot reads the CTB `--plot-style` names from the folders `AGENTDRAFTER_PLOT_STYLES` lists (or `--plot-styles`), such as AutoCAD's `Plot Styles` folder; with none named it plots monochrome. Tests write their own made-up CTB files.
- Test: `cargo test --workspace`.
- The viewer (`docs/viewer.md`): `npm ci` and `npm run build` in `viewer/` build the page into `viewer/dist/`, which the next `cargo build` embeds; they need Node 24, the `wasm32-unknown-unknown` target and the `wasm-bindgen-cli` the viewer crate pins. Without them `cargo build` still works and the binary serves a note in the viewer's place. `npm test` runs the page's unit tests, and `node e2e/run.mjs` the page in headless Chromium against `agentdrafter serve`. CI's `Viewer` workflow runs both; it is not on the merge bar.
- Before pushing, run what CI runs: `cargo fmt --all --check`, then `cargo clippy --workspace --all-targets --locked -- -D warnings`, then `cargo test --workspace --locked`, then `python3 -m unittest discover -s tools/judge/tests`, then the speed bench, small, with no number held: `python3 tools/bench/bench.py --bin target/debug/agentdrafter --only cold,set --runs 2 --sheets 16 --set-runs 1`. When the Python library, the command or a command changed, also build the wheel, install it into a virtual environment inside the checkout and run `python -m unittest discover -s python/tests` with that environment's Python, as CI's `wheel` jobs do on every system (`docs/python.md`).
- Prove a change to DWG reading or writing with the judge, `tools/judge/judge.py`; its README says how it works and what it cannot see. Run it from forge. It drives AutoCAD on the laptop over ssh, one AutoCAD at a time, after a free-memory check. Its settings live outside the repository, in `~/.config/agentdrafter/judge.toml` or `AGENTDRAFTER_JUDGE_*` variables. A run takes minutes, so start it in the background with its output in a log, and tell Zach when it starts.
  - A new file: build it with `agentdrafter build`, copy the DWG to a folder outside the repository, and run `python3 tools/judge/judge.py built <folder>`. It passes when AutoCAD opens it without recovery and its audit finds no errors. Add `--show-names` only when every drawing in the folder is public, such as the demo plant.
  - A revision or round trip: write each sample drawing back as `<id>.dwg` into a folder inside the judge's private folder, never in the repository. Then run `python3 tools/judge/judge.py roundtrip <folder> --name <run>`. It reports drawn objects identical, lost and changed, per drawing and pooled. Read them against AutoCAD's own plain save, which keeps 99.64% identical over 50 drawings.
  - Say in the pull request what the judge found: neutral IDs and counts only, never a drawing's name, path or content. The judge never runs in CI; CI runs only its tests, on made-up data.
- Report the speed baseline when a pull request could move it (`docs/speed.md`). `tools/bench/bench.py` measures its three numbers, one command from a cold start, a 100-sheet set built to DWG and PDF, and a change showing in the viewer, and prints them as JSON. Measure them on forge, against `agentdrafter` built in release with the viewer's page in, and give them in the pull request beside forge's baseline in `docs/speed.md`, as that page shows. A pull request could move them when it changes code that runs when `agentdrafter` runs, in `crates/` or `viewer/` beyond their tests; a dependency, the toolchain or a build setting (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `viewer/package.json`, `viewer/package-lock.json`, `pyproject.toml`); or what the bench measures and how (`examples/demo-plant/`, `tools/bench/`). One that changes only documents, tests, CI, the judge or other examples need not. No number is a gate: CI runs the bench small to check that it still works and holds it to nothing. The laptop's numbers are measured again with `tools/bench/laptop.py` only at a release or when Zach asks, against the Windows binary with the viewer's page that CI's `Windows binary` workflow builds, which is not on the merge bar.
- CI runs on GitHub's Windows, Linux and macOS runners, never on Zach's laptop.
- A DWG that AgentDrafter wrote is proven by AutoCAD: it opens without recovery, its audit finds no errors, and AutoCAD's own reading of the result matches its reading of the original outside what was changed. AutoCAD is the judge in tests on a machine that has a licence. It is never part of a job and never part of CI.
- Anything a reviewer will see, starting with the viewer, is shown as a prototype that opens on a phone before it is built for real.

## The merge bar

A pull request merges only when these jobs are green on its latest commit, all of the `CI` workflow (`.github/workflows/ci.yml`) but the last:

- `check (ubuntu-latest)`
- `check (windows-latest)`
- `check (macos-latest)`
- `demo plant (the same on every system)`
- `wheel (ubuntu-latest)`
- `wheel (windows-latest)`
- `wheel (macos-latest)`
- `viewer (build, unit tests, browser tests)`, of the `Viewer` workflow (`.github/workflows/viewer.yml`)

Each `check` job runs formatting, lints with warnings as errors, and tests, and builds, plots and checks the demo plant. The `demo plant` job compares the demo plant's DWGs and PDFs from the three systems byte for byte, and each `wheel` job builds the pip package, installs it in a clean virtual environment and runs it The `viewer` job builds the viewer's page, runs its unit tests and checks the page in headless Chromium (`docs/viewer.md`). Zach decided on 2026-11-11 that all three kinds join the merge bar. The ruleset `main merge bar` on GitHub requires these jobs and a branch up to date with `main`. A pull request that touches DWG reading or writing also states the judge's result before it merges.
