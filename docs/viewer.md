# The viewer

The viewer is the browser window where the reviewer watches a drawing set change, steps through its journal, and accepts or undoes (see [`CONTEXT.md`](../CONTEXT.md)). It draws a set's sheets in the page, with the same Rust drawing pipeline that makes the PNG and the PDF, compiled to WebAssembly, with TypeScript and React around it (ADR-0011); the reviewer pans and zooms on a laptop and on a phone. It sits in the [drafting app](drafting-app.md)'s frame ([below](#the-frame)): a ribbon, a tab for each sheet, the drawing as dark model space with the command bar under it, a status bar, and the journal in a panel on the right. A change set an agent sends shows as it lands, named by a toast, its objects marked; the journal steps back through the set as it was; a tap selects an object, whose quick properties open beside it; Undo last and Accept are always in reach; and its first [drawing tools](#drawing-tools), Line, Circle, Rectangle, Text, Move and Erase, draw and edit through change sets, as an agent does.

## Opening it

`agentdrafter serve` serves the viewer at `/`, beside the HTTP API ([servers.md](servers.md)). Start it in a drawing set's folder and open the address its start line gives under `viewer`:

```
cd examples/demo-plant
agentdrafter serve
{"ok":true,"result":{"address":"127.0.0.1:7316","listening":"http://127.0.0.1:7316","local_only":true,"token_required":false,"viewer":"http://127.0.0.1:7316/"}}
```

The page shows the drawing set in the folder the server started in. Its address can name another, and a sheet: `/?source=examples/demo-plant&sheet=DP-LD-102`, where `source` is a drawing set's folder, a sheet description or a DWG, as the server's folder names it, and `sheet` one of its sheets (the first without it). The address keeps the sheet shown, so a reload shows it again.

**From another machine or a phone**, such as over the tailnet, the server listens on an address beyond the local machine and needs its token:

```
agentdrafter serve --listen 100.101.102.103:7316
{"ok":true,"result":{"address":"100.101.102.103:7316", ... ,"token_required":true,"viewer":"http://100.101.102.103:7316/#token=3f9c…","token":"3f9c…"}}
```

Open the `viewer` address as printed. Listening on `0.0.0.0` prints `http://0.0.0.0:7316/#token=…`: put the machine's own name or address in its place.

## The token

A server listening beyond the local machine refuses every command without its token (`Authorization: Bearer <token>`). The viewer gets it this way:

- The start line's `viewer` address carries the token in its fragment, after `#`. A browser never sends a fragment to a server, so it reaches no server log, no proxy and no `Referer`.
- The page takes it from the fragment once, keeps it in the tab's session storage, and takes it off the address shown with `history.replaceState`, so it is not left in the address bar, the history or a link copied from it. A reload in the same tab keeps working; a new tab needs the address again; the server makes a new token each time it starts.
- The page sends it as `Authorization: Bearer` with every command, and never in a query string. A token in a query string is not taken.
- The start line is the only line the server writes the token in.

The page's own files are served without the token, since a browser cannot send one to open a page: `GET /` (or `/index.html`) and `GET /assets/<file>`, the files `npm run build` wrote, embedded in the binary. They are the page's code and nothing else, no drawing and nothing of the machine's; every drawing comes from a command, which needs the token. Only `GET` and `HEAD` reach them. On the local machine they are served, as commands are, only to a request addressed to the local machine by its `Host` and any `Origin`; the guards of the HTTP API (`Host`, `Origin`, JSON bodies) stay as they are for every command. The page is sent with a Content-Security-Policy that lets it run its own scripts and WebAssembly and talk to its own server only (`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`), with `Referrer-Policy: no-referrer`. `index.html` is never cached; the assets, whose names carry a fingerprint of their bytes, are cached for good.

## What it draws, and how

The engine stays on the machine that holds the drawings. The page asks it for a sheet with the `display-list` command, which reads the record and lays the sheet out, text in that machine's fonts, and replies with the sheet's display list: the shapes the PNG and the PDF draw from, as JSON, with the set's sheets, the paper and how many millimetres of paper a drawing unit spans. A demo plant loop sheet's reply is about 290 KB: 116 items, 5,582 segments. While Object snap is on, the page asks for the set as it is with `snaps` too, so the reply also gives every object snap of the objects the page draws itself ([below](#object-snaps)): 458 of them on DP-LD-101 and 475 on DP-LD-302, which make the reply 35 and 36 KB larger, about 12%. The set as it is comes with `origins` too ([below](#drawing-tools)): each object says whether its sheet's template or its row writes it, and the reply names the template and every sheet built from it, and on a sheet drawn in a layout the space a new object goes in (`space`), which the template warning and quick properties need; it adds about 30 bytes an object. The page keeps each sheet it has drawn, so going back to a tab asks the server nothing.

The page's renderer, `crates/agentdrafter-viewer`, is Rust compiled to WebAssembly. It reads the reply with the core's own types and draws it with WebGL2:

- **In the display list's order**, as the PNG paints it: a later item covers an earlier one, a blue line over a red one where they cross, a fill over the line under it. Nothing is blended. Items next to one another that draw strokes, or fills, are drawn by one draw call, run after run, and the GPU applies each draw's triangles, and each draw, in order: a demo plant loop sheet, all strokes, is one draw call. A sheet whose strokes and fills alternate more than 64 times is drawn instead in two draws, every item at a depth by its place in the list, a later one nearer, so the depth test keeps the later item's colour in every sample.
- **Strokes**: each segment of each stroke is a quad exactly as wide as its pen and long enough for its round ends, so every pen is as wide as the PNG draws it. The samples the quad's sides cover are the pen's; at a round end the fragment shader works out the share of the pixel the pen covers, by its distance, and that share of the pixel's samples is written (alpha to coverage). Each sample is written opaque, so where one stroke's segments overlap at a corner they cover the same samples once, and the canvas's multisampling, four samples a pixel, smooths the edges.
- **A viewport's contents**, a sheet's model space seen through a viewport of its layout, keep the viewport's window: the stroke shader draws none of a segment's ink outside it, as the PNG cuts it with a mask and the PDF with a clipping path. Fills are cut at the window already.
- **A clipped viewport's contents** draw through the stencil: the boundary's outline, from the display list's `clip_boundaries`, is cut into a fan of triangles from its first corner, which is drawn into the stencil first, each triangle inverting it, leaving it set inside the boundary by the even-odd rule; the viewport's strokes and fills then draw only where it is set, ink, round ends and fills cut at the boundary, as the PNG's mask and the PDF's clipping path cut them. The items seen through one clipped viewport are a run of their own, and a sheet drawn by depth draws them as a span of their own.
- **Fills** (solid hatches, TrueType text) are cut into triangles once, by their fill rule, with [lyon](https://crates.io/crates/lyon_tessellation); the multisampling smooths their edges.
- **Colours** are the [screen colours](../CONTEXT.md): index 7 white on the dark model space, as on AutoCAD's dark screen, where the PNG and the PDF plot it black on white paper. The other standard colours, 1 to 9, show as the picked prototype shows them, lifted where AutoCAD's own would be hard to read on the dark ground (its pure blue, index 5, shows as `#4f7cff`); every other index shows in the colour it plots in. Each segment and fill carries both its screen colour and its colour on paper, and the renderer draws with one or the other: a test's capture draws as the PNG ([below](#measured-against-the-png)). The PNG and the PDF are not touched: the demo plant's are the same, byte for byte, before and after the frame.
- **Pens are widths on paper**, as in the PNG and the PDF: a 0.5 mm pen is twice as wide when the sheet is shown twice as large. The finest pen is one CSS pixel wide, as a PNG's finest is one pixel.
- **Model space** is dark (`#212830`), and the paper is a dashed outline on it, one CSS pixel wide, where the sheet's declared paper ends; a sheet with no paper, such as a DWG, has its outline round its extents with the 5 mm margin a render leaves.
- **The grid**, when Grid is on (F7), draws behind the drawing: a line each quarter inch and a stronger one each inch on a sheet in inches or feet, each 10 mm and each 50 mm on any other. Lines closer than 8 CSS pixels are left out, and zoomed out further the grid steps out ten times as often as it needs. Model space, the grid and the paper's edge are one draw of a quad over the canvas, whose shader works out each pixel, so the grid costs the same at any zoom (`src/grid.rs` spaces it).
- **Panning and zooming** change two numbers the GPU is given; the sheet is laid out once, when it loads. Curves are drawn within a 100,000th of the sheet's larger side, finer than a pixel at the closest zoom.

It needs WebGL2 and nothing newer. It never asks for WebGPU, which Linux's system webview lacks and iPhones have only from iOS 26. A browser without WebGL2 shows that it has none.

## Pan and zoom

As the picked prototype does:

- **Touch**: one finger drags the sheet and flings it on release; two fingers pinch, keeping the point between them under them, and pan as they move; a double tap zooms in where it lands.
- **Mouse and trackpad**: drag to pan; the wheel zooms where the pointer is, as AutoCAD's wheel does; a trackpad's pinch zooms faster; a double click zooms in. Zach decided on 2026-11-11, after trying the viewer, that the wheel zooms.
- **Buttons**: zoom in, zoom out and Fit in a column at the right of the drawing, half way down, as the picked prototype has them; a phone shows only Fit, beside the command bar, where quick properties never cover it.

The sheet can zoom out to half its fitted size and in to 32 times it, and is never flung out of sight.

**The fit.** A sheet is fitted to the screen when it is first shown and on every change of tab: the whole paper, 10 pixels in from the edges, above the command bar (and a phone's bottom sheet under it) and, on a laptop, clear of the zoom buttons. The command bar counts as one line tall, so a prompt that wraps grows over the drawing without moving the fitted sheet. Until the reviewer pans or zooms, the view follows the fit: when the canvas changes size, as a browser may while it settles, or the pixel ratio changes, or the bottom sheet's peek does, the sheet is fitted again. Once the reviewer has moved it, a change of size keeps the point at the middle of the screen where it was, and the fit button fits it again. A fit, or a change of size or tab that fits the sheet, stops a glide still running, so the glide's next frame cannot put back the view it was heading for.

**Line weights.** A line is drawn at its pen's width on paper, so it grows as the sheet is zoomed in, as the plot would look under a magnifier; the thinnest line is one CSS pixel, so it stays visible on a phone. Zach decided on 2026-11-11, after trying the viewer on his phone, to keep lines like paper rather than thin hairlines at every zoom.

## The frame

The viewer sits in the drafting app's frame (#150), built from the prototype Zach picked on 2026-11-18, kept as the tag [`prototype/drafting-app-frame-150`](https://github.com/millZach/AgentDrafter/tree/prototype/drafting-app-frame-150/prototypes/drafting-app-frame): AutoCAD's look, cut down for beginners. On a laptop (900 CSS pixels wide or more), from the top:

- **The title bar**: AgentDrafter, **Undo last** with the change set it would undo, the set and the sheet shown, the status chips, and **Accept…**. The chips say how many change sets are not issued, or which accept issued the set, whether the set is inconsistent, and how many checks fail; stepping back, one amber chip says which entry is shown ([below](#stepping-through-the-journal)).
- **The ribbon**: Draw (Line, Circle, Rectangle, Text) and Modify (Move, Erase), each tool with its icon and name, and the Layer box. Hovering a tool shows its tip: its name, AutoCAD's alias (`L`, `C`, `REC`, `T`, `M`, `E`) and what it does in plain words; clicking or tapping it, or Enter on it, starts it ([below](#drawing-tools)), and it shows pressed while it runs; clicking it again ends it. The Layer box sets the [current layer](#the-current-layer), with a swatch of the colour it shows in; while an object is selected and no tool runs, it shows that object's layer instead.
- **A tab for each sheet**, with today's dots: inconsistent (!), fails a check (red), or has change sets not issued (blue).
- **The drawing**, dark model space with its grid and the paper's dashed edge. Toasts sit at its top left.
- **The command bar**, under the drawing, prompts in plain words with options to click: `Type a command, such as L for Line, or select an object, or click a snap to read its point` (on a phone, `Pick a tool in Tools, or tap an object to see it; touch and hold to read a point`); `FT-101 selected [ Move Erase Clear ]`; `Endpoint of FT-101: 2.3000, 6.5000 in [ Copy as snapped point · Clear ]`; `Showing entry 6 as it was, read-only [ Older Newer Live ]`; `Reaching the server… changes show when it is back`; and a running tool's prompt ([below](#drawing-tools)). It has a field that takes what is typed: on a laptop typing anywhere on the page goes into it, as in AutoCAD; on a phone **⌨ Type** opens it, with the phone's keyboard. Its note says what the keys do now. Over the drawing just above it, the last two lines of what happened: the journal read, a tool's points, a change set sent and landing, a selection, a toggle.
- **The status bar**: a sheet drawn in [several layouts](sheet-description.md#several-layouts) has a tab for each at its left, as AutoCAD's layout tabs are, in the order of AutoCAD's tabs, the first shown first, in a strip that scrolls when there are more than the bar has room for beside its controls; the address names the layout shown, `layout=`, as it names the sheet, and each layout is drawn from its own display list (`display-list --layout`). Then the cursor's place on the drawing in its units, to four decimals (`1.7200, 6.5000 in`), the snapped point's with the snap's name when the cursor holds one ([below](#object-snaps)), never cut short: on a narrow bar the layout strip and the paper give way to it, which follows the view as it moves under a still pointer, as after a fling, the paper and its units (`ANSI B landscape, inches`; paper declared by its size alone, `17 × 11 in`; none, `Extents, inches`), the units as the core gives them; with none from the core, the page cannot tell a drawing that states no unit (a DWG whose INSUNITS is 0) from one whose unit the core does not carry, so it shows no unit word and coordinates with no suffix (`Extents`), never one guessed from the scale, **Grid** (F7), which draws and takes away the grid, **Object snap** (F3), which turns the [object snaps](#object-snaps) on and off, with the ▴ beside it that opens their menu, **Ortho** (F8), which holds Line and Move level or upright ([below](#drawing-tools)), and the connection to the server: live, reaching it, or the entry shown.
- **The side panel** on the right: the **Journal**, and beside it **Assistant · Soon**, which holds the assistant's place until build 8.

Escape steps back out of one thing at a time: the template dialog, the Accept dialog, the snaps' menu, a phone's open ribbon, the tool running, what went wrong with what was typed, the selection, then an entry shown.

**On a phone** the drawing keeps the screen. The title bar holds **Tools** and the chips, which wrap onto a second line rather than be cut off; Tools opens the ribbon over the drawing, with Grid, Object snap and Ortho in it, since the status bar is hidden, and tapping a tool folds it again. A sheet's layout tabs are a row under the sheets' tabs. The journal is a sheet that peeks up from the bottom, dragging up to half or nearly all of the screen; its peek always holds the connection, the newest entry of the journal, and Undo last and Accept. The command bar sits above the peek, and Fit beside it.

## Watching change sets land

The page watches the set's journal through the server's event stream, `POST /events` ([servers.md](servers.md#watching-a-set)), which sends the `journal` command's reply when it opens and again each time the journal changes on disk. Every change set, failed attempt, undo and accept adds to the journal, so the page sees each one whichever process sent it and through whichever interface: an agent's command line in another terminal, its MCP server, the Python library or the HTTP API. A browser's `EventSource` sends no headers, so the page reads the stream with `fetch`, which sends the token as every command does; a stream that ends is opened again, a second later and then more slowly.

For each new entry:

- **The sheets it touched are drawn again**: those a change set landed on, and those of the change sets an undo undid. A sheet shown is asked for at once and drawn in place, keeping the reviewer's view; another is asked for when its tab is opened. A failed attempt and an accept change no file a sheet is drawn from.
- **A toast names it**, as the picked prototype's does: a change set that landed and on which sheets, one that landed on some sheets and failed on others, with the set inconsistent until they are fixed, one that failed whole, one that landed and failed checks, with the first failed check, an undo, and an accept, with the interface it came through. A change set's toast has a Show button, which shows the change.
- **Its objects are marked.** The change set's journal entry names each object it added, changed or moved on each sheet it landed on ([journal.md](journal.md#what-it-records)); on the sheet shown, each gets a halo round what it draws, green for added and amber for changed, which pulses three times as it lands and then holds, as the prototype's do. A deleted object draws nothing to mark.
- **The checks are run again** on the sheets it touched, from the saved files, for the header, the tabs and the toast.

The reviewer looking at the set as it was at an entry ([below](#stepping-through-the-journal)) is not moved: the toast still comes, and Show takes them back to the set as it is. Zach decided this on 2026-11-11, after trying the viewer: the page stays where the reviewer put it when a change set lands, and the toast with its Show button is how they reach it.

**A drawing kept is never older than the sheet.** Each sheet's drawing is kept with its generation: the sheet's version, which each entry that touches it moves on, and an epoch the whole journal shares. A reply that comes after its sheet's version moved on, such as one asked for before a change set to that sheet landed, is not kept, so going back to the sheet asks for it again. A journal that grows shorter, as when a change set's commit is rolled back, or whose entries already seen were replaced, moves the epoch on: every drawing kept, as the set is and as it was at an entry, is dropped and drawn again, and the checks are run again.

## Stepping through the journal

The bottom sheet lists the journal's entries, the newest first: change sets, failed attempts, undos and accepts, each with its number, what it did in a few words, the sheets it landed (✓) and failed (✕) on, its time and what has become of it: landed, failed check, inconsistent, undone, issued, failed attempt, undo or accept, and through which interface. Opening one shows its details: why it failed, its operations, what issued or undid it, and Undo for a change set an undo can take, with every later one.

Stepping to an entry, with the arrows or by opening it, **shows the set as it was just after that entry, read-only**: the page asks `display-list` for the sheet with the entry (`entry`), which the server rebuilds in memory from the undo states and never writes ([journal.md](journal.md#the-set-as-it-was-at-an-entry)). The view moves to a sheet the entry touched and zooms in on its marked objects. **The header's status chip says which entry is shown**: it turns amber and reads `Entry 3 of 5 · Live ›`, and tapping it goes back to live, to the set as it is. Zach chose this on 2026-11-11 from a mock of three places for it, so that nothing is drawn over the drawing, which looks a little warmer (sepia) while it shows the set as it was. Undo last, Accept and each entry's Undo are switched off while stepping, since they act on the set as it is, not the one shown. An entry whose files are no longer kept, because the undo state that held them was pruned (only the 50 newest change sets keep theirs) or the change set was undone, says it cannot be shown, and why, over the drawing.

## Selecting and quick properties

A tap, or a click, selects the object drawn nearest it, within 16 CSS pixels: the core picks it from the display list the page draws, in WebAssembly (`pick` in `src/draw/pick.rs`), so what is selected is what is drawn there, an insert for everything its block draws, and the page holds no hit-test of its own. The selected object gets a blue halo, and its **quick properties** open: on a laptop beside it, to its right or, without room there, to its left, following it as the drawing is panned and zoomed; on a phone as a card above the command bar, at its real height, a wrapped prompt's among it, and above the journal however far it is raised; on a phone held on its side, at the right of the drawing. The object is brought into the part of the drawing the card leaves free, above it or left of it, measured from where the card begins, if the card would cover it. When the journal comes to rest at another height or the command bar changes height, the view moves again only if that newly hides an object that was on the screen and clear of the card; an object the drafter panned away is left where they put it. They show its name, with a swatch of the colour it shows in, the checks it fails, its type (an insert's block), layer, ID, name and block, an insert's attributes, and the change sets that changed it, each of which shows its entry. They only show: editing in them is build 5. The selection follows the object by its ID as the sheet is drawn again, so a change set that deletes an object before it leaves it selected; once the object itself is gone, nothing is. A tap on nothing, the card's ×, the command bar's Clear or Escape clears it. The `display-list` reply says what each object is, by its place, which is what quick properties show.

## Object snaps

The cursor catches AutoCAD's [object snaps](../CONTEXT.md) on the drawing, as the prototype Zach picked on 2026-11-18 shows them (#151), kept as the tag [`prototype/drafting-app-snaps-151`](https://github.com/millZach/AgentDrafter/tree/prototype/drafting-app-snaps-151/prototypes/drafting-app-snaps). With no drawing tool running, a snap clicked is read out; a running [drawing tool](#drawing-tools) takes it as its point, and sends it as a snapped point.

**Where the snaps come from.** `display-list` with `snaps` gives every point the core's snap code finds on the objects the page draws itself, the code `query snap` answers with (`crates/agentdrafter-core/src/display_snaps.rs`): each object's own endpoints, midpoints, centres, quadrants, insertion points and nodes, an insert's in its block's geometry, and every intersection between two objects whose geometry's boxes overlap, the geometry as it is and not as a linetype dots it, found through a grid so a sheet of many objects is not every pair, listed once under the earlier object `with` the later. With them come the display list's `edges`, the fills whose edges the nearest snap finds a point on: a polyline's with width, a solid's and a donut's, and no text's or hatch's. The renderer works out each one's outline once, the pieces of its edges with the fill on one side only, so the seams where a wide polyline's segments meet, inside what is drawn, catch nothing. Each names its object by its place, its snap, `which` of its points and, for an intersection, the other object, so a snap here and the same object, snap and `which` asked of `query snap` give the same point, as a test holds on every sheet of the demo plant. Model space seen through a viewport, and objects on a layer that is off or frozen, an object of a block among them, which draw nothing of their own on the page, have none; a clipped viewport snaps on the boundary it is drawn as. The page asks for them only while Object snap is on, and for the sheet again with them when it is turned on; the set as it was at an entry comes without them: it is read-only, and nothing snaps there.

**The nearest snap, with no round trip.** The renderer, `crates/agentdrafter-viewer`, holds the sheet's snaps and, on each move of the mouse, finds those of the running snaps within 12 CSS pixels of the cursor (a finger's 22): nearest first, and of those within 2 pixels of the nearest, AutoCAD's order, endpoint, intersection, midpoint, centre, quadrant, insertion, node, nearest (`src/snapping.rs`). Nearest, when it runs, is the nearest point of what the page draws, found by the core's `nearest` beside `pick`, and is taken only when nothing else is in reach, as it lies everywhere on every object. On a demo plant loop sheet the search takes about 2 microseconds a move. **Tab** steps to the next snap in reach, while the drawing has the keys: from a focused button or field it moves the focus on, as on any page, until a press on the drawing gives it the keys back. Two snaps of one kind at one point are one; at the same place seen from above but at different heights they are two. A click takes the snap at the click itself, found then, not the one the cursor last caught.

**What the drafter sees.** On a laptop the renderer draws AutoCAD's model-space crosshair in place of the arrow, arms of 40 CSS pixels and the pick box in its middle, and the snap's AutoSnap marker in AutoSnap yellow, edged dark: a square for an endpoint, a triangle for a midpoint, a circle for a centre, a diamond for a quadrant, an X for an intersection, two squares for an insertion point, a circled X for a node, an hourglass for the nearest point (`src/overlay.rs`). Beside it the page puts a tag that names the snap and its object, such as `Endpoint · FT-101`, both of an intersection's, and which of the snaps in reach it is when there are several (`2 of 3, Tab`). The status bar's coordinates show the snapped point exactly, with the snap's name, `2.3000, 6.5000 in Endpoint`.

**A snap clicked** with no tool running reads out its point, as AutoCAD's ID command does, and selects its object: the command bar says `Endpoint of FT-101: 2.3000, 6.5000 in [ Copy as snapped point · Clear ]`. **Copy as snapped point** copies the [snapped point](change-sets.md#snapped-points) a change set's operation takes for it, `{"snap": {"id": "DP-LD-101/device", "snap": "endpoint", "which": "objects[3].from"}}`, an intersection's with its `with`; the nearest point, which a snapped point takes only from another snap, and an object with no ID, such as one of a DWG, are read out with no Copy. The read-out and its Copy go when what they name does: another sheet or layout asked for, or an object the point names, its own or an intersection's other, gone from the sheet. A page opened over the tailnet by its address is not a secure context and has no Clipboard API: it copies with the browser's older copy command, which a click still allows, and if that fails too the read-out gives the snapped point in the command bar's history.

**Object snap (F3)** turns snapping on and off. The ▴ beside it on the status bar, or a right-click on it, opens the **Object snap menu**: each snap with its marker and a line on what it means, ticked when it runs, an on/off switch, **Defaults** and **Clear all**. Ticking a snap while snapping is off turns it on. Perpendicular and Tangent are listed under "Inside a drawing tool, from the last point: coming": they will act only in a tool, from its last point, and are not built yet. The **running snaps** by default are Endpoint, Midpoint, Centre and Intersection: AutoCAD's defaults (OSMODE 4133) less Extension, which the core has not got, and with Midpoint, which a beginner reaches for first. Object snap and the running snaps are remembered in this browser, in its local storage (`agentdrafter-object-snaps`), as AutoCAD keeps OSMODE; a private window that keeps nothing keeps them for the visit.

**On a phone**, a finger reaches a snap within 22 CSS pixels. Touch and hold for 350 ms: a magnifier comes up above the finger, the drawing under it three times larger with the crosshair and the marker of the snap it would take, its tag under it, and follows the finger; lifting takes the snap, read out as a click's is, or says there was none under it. A second renderer draws the magnifier, on a canvas of its own, from the same display list. A quick tap still selects, and one finger still pans, once it has moved 6 pixels from where it went down, as a mouse does; a gesture that panned is never also a tap. A finger that moves on more than 3 pixels, short of panning, rests anew where it is, and the magnifier comes 350 ms after that, where the finger is. A second finger puts the magnifier away, with nothing taken, and pinches. A change that lands while a finger is held draws the magnifier anew, and the snap lifted is found again where the finger lifts, on the sheet as it is then and of the snaps running then: Object snap turned off from a keyboard during the hold takes nothing. A finger whose lift comes 350 ms or more after it came to rest, by the events' own times, was held, though a busy page got the lift before its timer: it takes the snap where it lifted, not a tap. A finger is judged by its own events' times, when it moved, not by when the page handled them: on a slow device, where a dragging finger's moves can reach the page after the hold was due, a magnifier that came up meanwhile goes again, with nothing taken, as soon as a move made before the hold was due arrives. The menu is in Tools, under Status, as **Snaps…**.

## Drawing tools

The first drawing tools (#152), built from the prototype Zach picked on 2026-11-19, kept as the tag [`prototype/drafting-app-tools-152`](https://github.com/millZach/AgentDrafter/tree/prototype/drafting-app-tools-152/prototypes/drafting-app-tools): **Line**, **Circle**, **Rectangle**, **Text**, **Move** and **Erase**, as AutoCAD's LINE, CIRCLE, RECTANG, TEXT, MOVE and ERASE run them, cut down for beginners. Each starts from the ribbon, from its alias typed in the command bar (`L`, `C`, `REC` or `RECTANG`, `T` or `DT`, `M`, `E`, in any case), or, for Move and Erase, from the selected object's command bar options. Enter at an empty prompt starts the last tool again. They draw only on a drawing set's sheet as it is: on the set as it was at an entry, a tool goes back to live first, on the object selected there found again by its ID, or on nothing when it is not on the set as it is, and a sheet description or a DWG, which a change set does not edit, says so.

**Where they run.** A tool's steps, its rubber band, its prompts and the change set it gives run in the renderer, `crates/agentdrafter-viewer/src/tools.rs`, in Rust, natively tested; the page passes it the clicks, taps and typing, draws the frame round its prompt, and sends what it gives. What an edit means is the core's: the tool sends one change set through the `change` command, with the operation the core has for what it does, and the core writes the set's records, builds the DWGs and records the change set in the journal, as for an agent's. So Undo last and Accept take a drafter's edit as they take an agent's, and an agent on any interface sees it land.

**What each sends**, one change set when it has what it needs:

| Tool | Steps | Sends |
|---|---|---|
| Line | the first point, then each next point; **Undo** takes the last back, **Close** (after two lines) closes back to the first, **Done**, Enter, Space, a right-click or Esc ends it, keeping what it drew | one `add_line` a segment |
| Circle | the centre, then a point on the circle or a radius typed; **Diameter** takes a diameter typed instead | `add_circle` |
| Rectangle | one corner, then the opposite corner, or its size typed as `@width,height` | a closed `add_polyline` of four points |
| Text | where it starts; **Height** sets its height; then the text, a line at a time, on the drawing on a laptop, Enter for the next line, Enter again or Done to finish; on a phone in a small box, with its height, and **Add** | one `add_text` a line, each line 5/3 of the height under the last |
| Move | the objects, picked one by one (a second pick takes one back) and Enter or Done, or the object selected first; a base point; then where it goes | one `move` an object, `from` the base point `to` the second |
| Erase | the objects, picked, then **Erase N** or Enter, or the object selected first, erased at once | one `delete` an object |

New objects go on the [current layer](#the-current-layer), in the sheet's row, as an object added on one sheet does ([change sets](change-sets.md#where-a-change-lands)), and on a sheet drawn in a layout in the paper space of the layout shown, as `display-list` with `origins` names it under `space`. Move does not take an object of model space seen through a viewport, whose points on the paper are not its own, and says so; Erase takes it. Text is drawn at 0.12 inches, or 3 millimetres, until a height is typed, which then holds for the session.

**Points.** A click, or a tap, takes the snap the cursor catches there ([object snaps](#object-snaps)), or the point itself, held level or upright with the tool's last point by **Ortho** (F8) in Line and Move; a snap wins over Ortho, as in AutoCAD. On a phone, touch and hold brings up the magnifier, the rubber band following the finger, and lifting takes the snap under it. The command bar takes a point typed in the sheet's own units: `x,y`; `@dx,dy` from the last point; `@length<angle`, the angle in degrees anticlockwise from the X axis; or, in Line and Move, a length alone, which goes that far towards the cursor (along X with no cursor), as AutoCAD's direct distance entry. A point clicked on no snap is kept to a ten-thousandth of the unit, as the status bar shows it; one typed, as typed; a circle's radius clicked, to a ten-thousandth too. While a tool takes points the crosshair loses its pick box and two quick clicks or taps are two points, not a zoom; a phone's double tap still zooms when no tool runs.

**Snapped points.** A point taken on a snap goes as a [snapped point](change-sets.md#snapped-points), its object by its ID, the snap, `which` and, for an intersection, `with`, so the core works out the exact place on the sheet as it stands. A Nearest point, and one on an object with no ID, goes as its coordinates. In an edit to a template's object, a snap on a row's own object goes as its coordinates too, since the core refuses a snapped point that is not the same on every sheet the template reaches. A move of several objects goes by coordinates, the same for each: the core moves one object after another and would find a snapped point again where the last move put it. One object's move keeps its snapped points, a snap on itself among them, since the core works its `from` and `to` out before it moves it.

**What it shows.** The prompt says what the tool wants, with its options to click (`LINE on wire Click the next point, or type @dx,dy or a length [ Undo · Close · Done ]`), and what went wrong with the last thing typed, in red under it. The rubber band is drawn in the current layer's colour: the line from the last point, the circle and a dashed guide from its centre, the rectangle, and for Move the objects in pale blue where they would go and a dashed guide from the base point; the points taken show as small blue squares, and each object picked has a blue halo. Beside the cursor, as AutoCAD's dynamic input, the length and angle from the last point, a circle's radius (or diameter) or a rectangle's size. A Text tool's lines show where they will go, at their height, in the current layer's colour, with a caret.

**The template warning.** Quick properties say where the selected object **comes from**: its template, which an edit changes on every sheet built from it, or its sheet's row. When the objects Move or Erase picks are a template's, the command bar says so while the tool runs, above its prompt: `This is part of the template. Moving it changes 7 sheets. You will be asked before it lands.` When the tool has what it needs, a dialog asks first, naming the template and every sheet built from it, the one shown marked: **Change all 7 sheets** sends the change set, which lands on each of them, all or nothing (ADR-0005); **Cancel** sends nothing. Zach decided this on 2026-11-19 from the prototype. The core says it: `display-list` with `origins` gives each object's `from`, `template` or `row`, and the sheet's `template`, its path and the sheets built from it, as the change set finds them ([servers.md](servers.md)).

**When it lands.** The page asks for the sheets the change set landed on as soon as `change` replies, without waiting for the journal; the journal's event then names it in a toast and marks its objects, as for any change set, and the sheet is not asked for twice. A change set that does not land, or lands on some sheets only, says why in a toast. After a Move, the moved object's snaps come from the core's next display list.

**On a phone** the options are buttons, without the brackets between them, and **⌨ Type** opens the field and the keyboard, for an alias, a point or a length; it is not offered beside a selected object's Move, Erase and Clear, so that the bar stays one line there, nor while the Text tool's box is open.

**While a change set is on its way**, Undo last and Accept wait, since the change set they would take may be about to land, until every change set the page sent has replied; the page sends them one after another, in the order the tools gave them, as when Erase on an object selected first ends a Text tool that kept its words. Once `change` replies, Undo last names the change set, before the journal's event does. The sheets a change set landed on are asked for once, by `change`'s reply or by the journal's event, whichever comes first.

**Keys.** Typing anywhere goes into the command bar's field; Enter or Space enters it (Space is a space while a text's words are typed); Esc drops what is typed and ends the tool, keeping lines and text it drew, or with nothing changed, while a Text tool's Cancel, and the phone's text box's, drops the line being typed; a right-click on the drawing is Enter, on what is typed, as AutoCAD's; Delete erases the selected object. F3, F7 and F8 work while a tool runs.

### The current layer

The Layer box lists the sheet's layers, as `query layers` gives them, asked for each sheet and again when the box is opened, a locked one and one not shown so marked, and sets the current layer, which every new object goes on, as AutoCAD's current layer. It starts as layer `0`; the page keeps the layer chosen for each drawing set in the browser's local storage (`agentdrafter-current-layer`), and goes back to `0` on a sheet that has not got it; until the sheet's layers come, it is the layer kept. The prompt of a tool that draws names it (`on wire`), and its rubber band is drawn in its colour.

## Undo and accept

Undo last and Accept are in the title bar on a laptop and in the bottom sheet's peek on a phone.

**Undo last** undoes the newest change set an undo can take, through the same `undo` command every interface reaches, as one ([journal.md](journal.md#undo)); the button names it. An issued change set cannot be undone, so after an accept Undo last is off until a change set lands.

**Accept** issues the working revision through the `accept` command ([journal.md](journal.md#accept)). It asks first, as the prototype's does: the page runs the accept as a dry run and shows what it would issue, the change sets and their sheets, and every failed check, or that all checks pass; **Accept and issue** accepts, despite the failed checks it listed, and only if the journal has not moved on since the dialog opened (`newest_seen`). An accept that cannot be made, the set inconsistent, or nothing to accept, says why in a toast and asks nothing. The journal records the accept as the viewer's. Zach decided on 2026-11-11, after trying the viewer, to keep the words **Accept and issue** and, once issued, **Issued (entry N)** in the header: an accept is named by its entry in the journal, and revisions are not lettered.

**An output folder outside the set.** A set whose `output` is outside its folder, such as `../issued`, is issued as any other: its PDFs say so, since their stamps start from the set's template, and so does a PNG or a PDF made from one of its DWGs alone, since each DWG's build mark names its set ([#50](https://github.com/millZach/AgentDrafter/issues/50), [the stamp](render.md#the-stamp)).

A tab shows its sheet at once when the page has drawn it before; the server is asked for each sheet once. Going back to a sheet already drawn shows it with nothing said of the sheet asked for meanwhile, whether that one is still coming (its reply is kept for later) or failed.

## Building it

The page lives in `viewer/`: TypeScript and React, built with Vite. `npm run build` there builds the renderer for WebAssembly (`cargo build -p agentdrafter-viewer --target wasm32-unknown-unknown --profile wasm-release`), makes its JavaScript glue with `wasm-bindgen`, checks the types, and writes the page into `viewer/dist/`. It needs Node 24 or later, the Rust target `wasm32-unknown-unknown` (`rustup target add wasm32-unknown-unknown`) and `wasm-bindgen-cli` of the version `crates/agentdrafter-viewer` pins (`cargo install wasm-bindgen-cli --version 0.2.130 --locked`, or `WASM_BINDGEN` naming the binary).

```
cd viewer
npm ci
npm run build
cd ..
cargo build -p agentdrafter-cli
```

**How the page reaches the binary.** `crates/agentdrafter-cli/build.rs` embeds every file of `viewer/dist/` in `agentdrafter` when it has been built. The built page is not committed: CI's `Viewer` workflow builds it and tests the binary with it. A plain `cargo build` on a machine without Node works: with no `viewer/dist/`, the binary carries a one-page note in its place that says how to build the viewer, and serves every command as before. This keeps generated WebAssembly and JavaScript out of the repository and out of every pull request's diff, and the required CI jobs need no Node. CI's `Windows binary` workflow, not on the merge bar, builds a Windows `agentdrafter.exe` with the page in, on each push to `main` and when asked, for the speed baseline's run on the laptop ([speed.md](speed.md)).

`npm run dev` serves the page from Vite on port 5173 and sends its commands on to `agentdrafter serve` on `127.0.0.1:7316`, for working on the page.

The page's packages, all permissive or MPL-2.0 (ADR-0010): `react`, `react-dom` and `scheduler` (MIT) go into the page; `vite` (MIT) with `rolldown`, `postcss`, `lightningcss` (MPL-2.0) and their helpers, `typescript` (Apache-2.0), `@types/*` (MIT) and `playwright-core` (Apache-2.0) only build and test it. The renderer's crates: `lyon_tessellation`, `lyon_path`, `lyon_geom`, `euclid` (MIT or Apache-2.0), `float_next_after` and `libm` (MIT), and `wasm-bindgen`, `js-sys` and `web-sys` (MIT or Apache-2.0).

### Measured against the PNG

The canvas is drawn at the view and size of `agentdrafter render --scale 1 --dpi <dpi>` of the same sheet, at one device pixel to a CSS pixel, in the paper look, white all round as a PNG's paper is and each colour in the colour it plots in, and read back. A demo plant sheet in the viewer is the set's sheet; its PNG is rendered from its DWG, which draws the same display list point for point. `viewer/e2e/overlap.yaml` is a made-up sheet of colours drawn over one another: a blue line over a red one, a black line over both, a green fill over the three, a red line over that and a yellow fill over part of it. `viewer/e2e/viewport-clip.yaml` is a made-up layout of lines 2.11 mm wide that a viewport cuts, round ends among them; `viewer/e2e/viewport-boundary.yaml` the same lines and a fill cut by viewports clipped to a circle and to a notched polygon; `examples/layout.yaml` is the layout example, and `examples/layouts.yaml`'s second layout, `Wiring`, is drawn as the address asks for it. A check of the layout tabs opens `examples/layouts.yaml` on a phone, finds a tab for each layout, picks the second, and finds it drawn and named in the address; on a laptop, it finds them at the left of the status bar; and with ten layouts (`viewer/e2e/ten-layouts.yaml`, made up) at 900 CSS pixels wide, the strip scrolls and Grid, Object snap, Ortho and the connection stay on the screen.

For every inked pixel of each image (its darkest channel below 192), the nearest pixel of the other image darker than 224 is looked for, within one pixel and within two, as ticket #11 measured the PNG against AutoCAD; and the nearest in the same colour, no channel more than 96 levels off. That is more than anti-aliasing moves an edge pixel, and less than red, blue or green differ from black, or from one another, even at half a pixel's coverage.

The tolerance the test holds:

- 99.9% of each image's ink within one pixel of the other's, and all of it within two;
- 99.7% of it within one pixel in the same colour;
- at most 0.5% of pixels differing by more than 64 levels in any channel;
- a mean difference under 2 levels in 255.

### Smooth on a phone

The `frames` check opens the demo plant's `DP-LD-101` (5,582 segments, one draw call) at phone size with touch and the CPU throttled four times (Chrome's `Emulation.setCPUThrottlingRate`). Through Chrome's own touch events, a finger moving every 8 ms, each event stamped with the time the finger made it, as a real finger's is, however long the page takes to handle each, it pinches out with two fingers, drags with one and lets go moving, and pinches in. It keeps the time of every display frame and of every draw of the canvas in each gesture, and how long each draw call took. It holds:

- every gesture draws the canvas at least 20 times;
- the page's own draw takes a median of 1 ms at most and 95% within 4 ms;
- the point under the fingers stays under them.

With the GPU (`--gl gpu`) it also holds:

- the canvas drawn on at least 60% of each gesture's frames;
- 95% of the times between draws, and between frames, within 20 ms, 99% within 34 ms (one refresh late at most), and none over 100 ms.

In software WebGL (the default without a GPU, and CI's runner) filling the phone's 1170 by 2532 multisampled canvas on the CPU, beside Chrome's own handling of the test's touches, is slower than a phone's GPU, so those times are reported, not held. On forge:
